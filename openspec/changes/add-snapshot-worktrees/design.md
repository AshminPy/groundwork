## Context

Verified on this host (git 2.43.0): `git worktree list --porcelain` prints blocks of `worktree <path>`, `HEAD <sha>`, `branch refs/heads/<name>` (or `detached`, `bare`, `prunable`), separated by blank lines. The per-checkout facts the snapshot already reads (`status --porcelain`, `rev-list --left-right --count @{upstream}...HEAD`) work unchanged inside any worktree.

## Decisions

DECISION            Surface only worktrees with uncommitted changes, unpushed commits or no upstream; count the rest, including those git could not read.
EVIDENCE            Measured on this repository: listing all eight siblings pushed the snapshot to its 2,500-character cap and cut off the verification-command line; listing only the two with local-only work (six pushed ones counted) was 341 characters, the whole snapshot 2,349, and everything else was kept.
WHY                 The value is "this work can be lost"; a clean, fully pushed worktree's work is on the remote and findable through branches and PRs. Alternatives that lost: list everything (noise, truncation); persist a model-written list of worktrees (a second source of truth that goes stale, which the repository state does not).
TRADEOFFS           A fresh session sees nothing about pushed siblings beyond a count; "No upstream" does not prove the commits are not on a remote (a fresh branch at a pushed commit is listed); the line says what it knows ("no upstream tracking branch", "upstream branch gone") rather than claiming the work is local-only. Over-reporting is accepted; hiding is not: a git failure, a timeout or a broken checkout is counted as "could not read", never as clean.
VALIDATION METHOD   Real git repositories with a bare origin in tests (dirty, ahead, no-upstream, detached, missing, locked, unreadable, caps, exhausted and clamped budget, `--separate-git-dir`, submodule, old-git shims, non-UTF-8 and hostile paths, section isolation), mutation checks (28 mutants of the section's safety and bounding clauses, all caught, runner in `tests/mutation/mutate_snapshot_worktrees.py`), a run against this repository's real worktrees.
UNCERTAINTY         A hard-mounted dead network path blocks in the kernel, where no Python timeout can interrupt it (the in-process `isdir`/`realpath` calls); the 10-second hook timeout then drops the whole snapshot. Not testable here (RUNTIME VALIDATION REQUIRED).

## Architecture-quality answers

- **What changes / what is configuration?** The limits are module constants beside the existing ones; nothing is configurable because a larger listing would crowd out the other facts.
- **Dependency unavailable?** `git` missing or failing for the listing: nothing printed for the section. A sibling git cannot read, or whose directory is missing or has lost its `.git`: counted as such. The rest of the snapshot is unaffected (fail-open, as before).
- **Observability?** The section is the observation; `git worktree list` is named in the line for the full picture.
- **Security boundary?** Branch names and paths are attacker-controlled in a hostile repository: they pass through the existing `clip()` (control characters stripped, per-field cap) and sit inside the existing data envelope; the listing uses `-z` (NUL-separated) when git supports it so a newline in a path cannot forge an entry. Siblings are read with `GIT_OPTIONAL_LOCKS=0`; the hook runs no other command in them. A sibling's own `.git` is not trusted: a directory whose `.git` is an empty directory is counted as unreadable without running git in it (verified: git would walk up and report the surrounding repository's state as the sibling's; a `.git` file that points nowhere makes git fail instead), and output from siblings is decoded with `surrogateescape` so a non-UTF-8 path is examined, not mislabelled as missing, then made printable before it is shown. Not handled: a hostile repository's own configuration (for example `core.fsmonitor`) still applies when git runs in a sibling; the hook already runs git in the session's own checkout under the same assumption, and the snapshot's existing trust model (a repository the user chose to open) is unchanged by this section.
- **Cost?** The listing, two `rev-parse` calls (top level and git directory) plus one more per entry that is a git directory itself, and at most 12 x one `git status -b`, all started before one deadline (3 s from section start, 8 s from hook start; each call's timeout clamped to the time left). Typically 0 to 2 siblings exist. Measured: with every git call slowed by 0.4 s and a 1.3 s budget the section ended in about 1.5 s with the remainder counted as not examined (test). Size: the section is built last and gets only the room the other facts leave under the 2,500-character cap (at most 700 for the summary, rows and the "… N more" line together), so it cannot push the verification commands or the closing instruction out; the baseline facts of a repository with eight OpenSpec changes and a long history can already fill the cap, and then only the summary line is shown.
- **Known limits.** A session in a linked worktree of a repository created with `--separate-git-dir` (or whose `.git` is a symlink) sees its main checkout as a git directory with no `core.worktree`, so that entry is counted as "whose state git could not read": honest, but a permanent false alarm there and a dirty main checkout is not surfaced. Branch names are cut from the left like paths (the end is the distinguishing part for generated names such as `worktree-agent-<id>`); a human prefix such as `feature/PROJ-123` is the part lost. The listing without `-z` (a git that rejects it) cannot tell a newline inside a path from a new entry, so an ambiguous listing is reported as such instead of guessed.
