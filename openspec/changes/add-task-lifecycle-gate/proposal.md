## Why

Groundwork's workflow rules say MATERIAL work needs an OpenSpec plan, owner approval before implementation, verification and an independent review. Today only the last step is enforced (the `require_material_review.py` Stop gate). Nothing records an engineering task when it arrives. Nothing stops implementation before the owner approves. Nothing keeps edits inside the approved scope. And nothing ties "complete" to observed evidence. A fresh session also cannot see which task was in flight or what it was waiting for. These are reminder-only rules today. The owner asked for them to be enforced in code (M1 of the Groundwork engineering-workflow programme).

## What Changes

- **Task intake.** A `UserPromptSubmit` hook classifies each prompt deterministically. It recognises a Jira-style key and engineering action verbs, and it skips questions, slash commands and system envelopes. When a prompt is a task, the hook registers it in a per-repository task ledger. It records the tier (MATERIAL or STANDARD), risk categories and an intake checklist of prerequisites and questions. For MATERIAL tasks it also creates the OpenSpec change (`openspec init --tools none` only when the repository has no `openspec/`, then `openspec new change <key>-<slug>`). A prompt that names a known task key gets that task's state injected instead.
- **Plan gate.** `groundwork task request-approval <KEY>` refuses until the plan exists, passes `openspec validate --strict`, has tasks, and has the sections Groundwork needs: Prerequisites, Risks, Missing Information, Estimate (a number plus stated confidence or uncertainty), Scope (specific path patterns) and Verification (exact commands). Optional Approved Operations lists the sensitive commands the plan authorises. When it passes, it records an approval code: a digest of the plan, with task checkboxes ignored.
- **Owner approval through a human-only channel.** The owner types `/gw-approve <KEY> <code>` (or `/gw-cancel <KEY>`). These are user commands, and they are accepted only through Claude Code's `UserPromptExpansion` event. That event fires when a person types a slash command, not when Claude calls a tool. Claude's attempts to invoke, schedule or send these commands are denied. Approval is bound to the plan digest. If the plan changes after approval, the approval stops applying until the owner approves the new plan.
- **Execution gate (`PreToolUse`).** While a MATERIAL task in the repository is not yet approved, only read-only work is allowed. File edits are allowed only inside the task's OpenSpec change directory. Bash commands must be on a read-only allowlist. Mutating MCP tools are denied. Once approved, edits must match the approved Scope. Sensitive commands (cloud, Kubernetes, Terraform, Helm mutations, recursive deletes, remote execution, mutating HTTP) must match an Approved Operation. The task ledger, the owner commands and, during a gated task, Groundwork's own hooks and settings cannot be changed by Claude. If the gate itself errors while a gated task is active, it denies (fail closed).
- **Evidence capture (`PostToolUse` / `PostToolUseFailure`).** Runs of the approved verification commands are recorded with their outcome and a fingerprint of the working tree. So are the results of foreground review subagents, including their `REVIEW RESULT` verdict. After every Bash, agent or MCP call, a git-based audit reports any change outside the approved scope to Claude immediately. That covers every execution path, not only the edit tools.
- **Completion gate.** `groundwork task complete <KEY>` sets the task to complete only when all of these hold: the approved plan is unchanged, every task is checked, no out-of-scope change exists, and every verification command succeeded on the current working tree after the last sensitive operation. An independent review on the current working tree must also report zero MUST FIX findings.
- **Continuity.** The SessionStart snapshot lists the repository's open tasks with state and next action. `groundwork task list|show` renders them. Tasks are stored per repository under `$CLAUDE_CONFIG_DIR/groundwork/tasks/`, never in the repository, so a cloned repository cannot ship its own approval. Projects and separate config directories (for example work and personal) never mix.

Not in this change: Jira fetching (intake only recognises the key), model-written effort numbers beyond the plan's own Estimate section, MCP catalog (M3), completion-claim text checks at Stop (M2), statusLine task display (M3).

## Capabilities

### New Capabilities
- `task-lifecycle`: task intake, the OpenSpec plan gate, owner approval, the execution and scope gate, evidence capture, the completion gate, and task continuity.

## Impact

New: `hooks/groundwork_tasks.py` (ledger, classifiers, plan checks, CLI), `hooks/groundwork_task_gate.py` (hook entry for five events), `commands/gw-approve.md`, `commands/gw-cancel.md`, `tests/test_task_lifecycle.py`, `docs/TASK-LIFECYCLE.md`. Changed: `scripts/merge_settings.py`/`unmerge_settings.py` (five more hook registrations), `install.sh`/`uninstall.sh`/`setup.sh` (copy, remove and verify the new files), `scripts/groundwork_cli.py` (`groundwork task` pass-through), `hooks/groundwork_session_snapshot.py` (open-task lines), `rules/engineering-workflow.md` (one paragraph naming the gate), `CHANGELOG.md`, `docs/ARCHITECTURE.md`. No new dependency. Python standard library only, plus the OpenSpec CLI that is already installed. No network access.
