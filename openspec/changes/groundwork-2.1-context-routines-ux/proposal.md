# Groundwork 2.1 — Context, Capabilities, Routines & UX

## Why

Groundwork 2.0 made engineering work evidence-first, reviewed, and continuity-aware. It did not change what the user has to remember: playbook names, persona names, which MCP to reach for, when to save state, when review fires. The 2.1 brief asks for the opposite experience — the user states the outcome, Groundwork resolves the workflow, context, role, tools and safety automatically — while explicitly forbidding the thing that experience usually costs: a bigger, heavier framework. This change is scoped by that tension. Nearly every section of the requesting brief includes its own escape valve ("implement only strong candidates," "defer if not supported, document why," "do not overengineer") — this proposal uses those valves deliberately, not as an excuse to skip work, but because building all 30+ requested surfaces at equal depth would itself violate the brief's own architectural principle (one owner per capability, prefer native/existing mechanisms, no giant framework).

## What changes (this pass — see design.md for full reasoning and what was deliberately trimmed)

1. **Context-engineering audit** (`docs/CONTEXT-ENGINEERING.md`, new) — a measured inventory of what enters context today (rules, playbooks, snapshot, ECC, MCP, skills) classified always/selective/lazy/isolated/persisted/reconstructed, plus the native mechanisms Claude Code already provides for lazy loading (progressive-disclosure skills, deferred-tool search, subagent isolation) that this change relies on instead of building anything custom.
2. **Capability resolution model** — a short rule-text addition (`rules/engineering-workflow.md`) stating the discovery order (repo tooling → native capability → trusted skill → trusted MCP → official CLI/API → browser → user) as judgment guidance, not a decision tree; and a **Routine** concept introduced alongside the existing Playbook/Role/Skill/Tool vocabulary (`rules/task-routing.md`), kept structurally distinct.
3. **MCP/integration capability matrix** (`docs/INTEGRATIONS.md`, new) — researched, evidence-backed guidance for GitHub, Spacelift, AWS, GCP, Kubernetes, Terraform, Jira, Confluence and observability. Documentation only: Groundwork does not install, configure, or store credentials for any of these — it tells the user what's trustworthy and how to wire it themselves, consistent with the existing "MCP/external tool access belongs to the task's own environment" ownership rule.
4. **Curated skills evaluation** (folded into `docs/FUTURE-SCOPE.md`) — teaching, task-observation, and general-purpose skill candidates evaluated against Groundwork/ECC/native overlap. Adopted only where the evidence justifies it; nothing installed automatically, `wshobson/agents` remains a documented candidate only, per the owner's explicit instruction not to auto-adopt it.
5. **Routines** — a new, generic scheduled-execution mechanism (`scripts/groundwork_routines.py`) extending the existing launchd/cron pattern already used for the health dashboard (`scripts/groundwork_report.py schedule`), not a new scheduler. Six concrete routines ship: Jira end-of-day update and a daily technical-news digest (both explicitly high-priority in the brief), plus weekly status, PR/review follow-up, a daily work/TODO digest, and a documentation-drift check — all built on the same framework (config → evidence gathering via a headless `claude -p` session → dry-run-capable output → verify-after-mutation → telemetry). Task Observer is evaluated and deferred, with the privacy/telemetry-schema gap that blocks it documented. The remaining "additional routine discovery" candidates (cert/PKI expiry, dependency advisories, infra drift, cost anomaly, stale-RCA follow-up, release readiness) are scored and recorded as future candidates, not built this pass — six built routines is already a real, testable surface; building all fourteen at once is exactly the overbuilding the brief warns against.
6. **Browser/Chrome governance** — a short rule-text addition applying the existing authorization model (§4) identically to browser-driven mutation, plus the explicit "read the result back before reporting VERIFIED" rule for browser and MCP/CLI mutations alike. No new code.
7. **Setup as a capability configurator** — `setup.sh` gains an optional profile + capability-selection flow (cloud/platform/integrations/skills/routines/news topics) on top of the existing three questions, persisting choices to one human-readable JSON file (`~/.claude/groundwork/config.json`, new `scripts/groundwork_config.py`) that upgrade preserves and `--configure` can revisit. JSON rather than the brief's own illustrative YAML example — it matches every existing Groundwork config file (`settings.json`, `report.json`) and needs no new parser; see design.md §G. The one-command path (`./setup.sh` with all defaults) still works unchanged for a user who wants none of this.
8. **`setup.sh --doctor` / `--configure` / `--routines`** — three new modes on the existing mode-dispatch pattern (alongside `--verify`/`--rollback`/`--uninstall`), not a new CLI framework. `--doctor` extends the existing `verify_install()` check with capability/routine rows, using real INSTALLED/CONFIGURED/CONNECTED/UNAVAILABLE/DISABLED distinctions, never asserting connectivity it didn't check.
9. **ECC pinning** — `install.sh`'s ECC install line moves from a floating `main` install to a pinned `#ref` install (using the version-pinning mechanism confirmed to exist on Claude Code's plugin-marketplace path), with clean-install/upgrade/rollback/uninstall/identity re-proven against the pinned form.
10. **Terminal UX** — resolved by the context-engineering/TUI research in this pass (see design.md); the existing HTML dashboard is retained regardless.

## What does not change

Ten playbooks, four dynamic builder personas (still dynamic, still no permanent agent files), automatic main/subagent/Agent-Team selection, the session-snapshot/continuity/investigation-continuity mechanism, the review gate, the push guard, telemetry's schema and privacy discipline, the evidence taxonomy, OpenSpec's role, ECC's role. This is deliberately an extension of 2.0's architecture, not a rewrite.

## Impact

- Rule files: `rules/engineering-workflow.md`, `rules/task-routing.md` (extended, not restructured).
- New scripts: `scripts/groundwork_routines.py`, `scripts/groundwork_config.py`.
- Modified scripts/installers: `setup.sh`, `install.sh`, `scripts/merge_settings.py`/`unmerge_settings.py` (routine/config state cleanup on uninstall).
- New docs: `docs/CONTEXT-ENGINEERING.md`, `docs/INTEGRATIONS.md`; `docs/FUTURE-SCOPE.md` extended.
- New tests across all of the above; full existing suite re-run, not modified.
- No new MCP servers, skills, or third-party dependencies are installed by default. No credentials stored anywhere in Groundwork's own files.
