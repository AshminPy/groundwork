# Groundwork 2.1 — design

Evidence gathered live 2026-09-28 (this session — see the design decisions below for exact sources; nothing here is asserted from training-data memory). Where evidence changed a section's scope from the brief's own draft, that is stated explicitly, in the same "correct in place, don't silently deviate" style Groundwork 2.0 used.

## A. Context engineering — findings drive the rest of this design

Full inventory: `docs/CONTEXT-ENGINEERING.md`. The load-bearing finding for everything below: **Claude Code already provides every lazy-loading primitive the brief asks for.**

- **Progressive-disclosure skills**: description always in context (truncated at 1,536 chars), full body loads only on invocation. Native, unchanged by this design.
- **Tool search**: on by default, defers MCP/on-demand tool schemas, loads up to 5 most relevant on demand, catalog supports 10,000 tools. **Directly observed in this very session** (this session's own tool listing works exactly this way), not just documented — the strongest evidence class available.
- **MCP lazy loading**: three independent layers — tool-schema deferral (tool search), a connection-level discovery cache (server doesn't even connect until first use), and `disabledMcpServers`/`enabledMcpServers` allow/deny lists in `~/.claude.json`.
- **Skill-level allow/deny independent of plugin install**: `skillOverrides` (on/name-only/user-invocable-only/off per skill, including a plugin's namespaced skills) and `Skill(name)` permission rules — confirmed this covers "let a user enable exactly the skills they picked at setup" without needing Groundwork to build a toggle system.
- **Subagent isolation**: only the final structured report crosses back into the parent context, never the subagent's own transcript — confirmed both by Anthropic's own docs and by this project's own implementation history (every research dispatch in this and the prior session behaved exactly this way).

**Conclusion, and the single biggest scope decision in this design**: no custom context-management, capability-router, or MCP-gateway code is built. The 2.1 "capability resolution model" (`engineering-workflow.md` §6a) is rule text telling the model to use these native mechanisms in a sensible order — it is guidance sitting on top of infrastructure that already exists, not new infrastructure.

## B. Capability resolution — shipped as rule text, not a router

See `engineering-workflow.md` §6a (shipped) and `task-routing.md` §4 (Playbook/Routine/Role/Skill/Tool distinction, shipped). Six steps, each escalating only when the previous one doesn't apply, ending in the user only for genuine decisions — this mirrors §4's existing autonomy rule almost exactly, which is deliberate: capability resolution and authorization are the same kind of decision (repository/native/trusted-source evidence first, the user only when evidence runs out), so reusing that rule's shape rather than inventing a parallel one is the smallest-sound-design call (`architecture-quality.md`'s own governing principle, applied to this design itself).

## C. Native local scheduling — extends the existing dashboard pattern, confirmed correct

Researched live against code.claude.com (2026-09-28). Finding: **none of Claude Code's three branded scheduling features fit a bare local CLI install** — cloud Routines require the hosted product (out of scope by the brief's own framing), Desktop scheduled tasks require the separate Desktop GUI app (Groundwork installs the CLI only), and `/loop` requires a continuously-running idle session and self-expires after 7 days (wrong shape for "runs even when nobody has Claude Code open"). Headless mode (`claude -p`) is explicitly documented as the general composition point for "any automated workflow." **Decision: extend Groundwork's own existing pattern** — `scripts/groundwork_report.py`'s launchd-on-macOS/cron-elsewhere scheduler, already proven in 2.0 — rather than adopt any of the three native features or build a new scheduler. This is not a fallback; it is the only mechanism that actually matches "runs unattended, on a bare local CLI install, without a continuously open session."

**Safe unattended invocation, confirmed via live docs research, is a specific flag combination, not `--dangerously-skip-permissions`**: Anthropic's own docs restrict that flag to containers/VMs and refuse it under root/sudo. The correct pattern for an unattended cron/launchd job is `--permission-mode dontAsk` (deny anything that would otherwise prompt) + an explicit `--allowedTools` allowlist scoped to exactly what the routine needs + `--permission-prompts none` (fail closed instead of hanging when nobody can answer a prompt). `--bare` is deliberately **not** used — it would skip Groundwork's own hooks/skills/MCP config, which routines need active to inherit the same evidence/safety discipline as an interactive session. No native run-length timeout exists; `scripts/groundwork_routines.py` wraps each invocation with a configurable wall-clock timeout itself.

## D. Routines — framework once, six concrete routines on top of it

`scripts/groundwork_routines.py` (new) owns: reading `~/.claude/groundwork/config.json`'s `routines` section, invoking `claude -p` per §C's safe pattern with a routine-specific prompt, capturing the result, recording telemetry, and — for mutating routines — supporting `--dry-run` and requiring a post-mutation verification step in the prompt itself (read the changed resource back before the routine may report success). One framework, not six bespoke scripts: each routine is a name + a prompt template + a `mutates: true/false` flag + an evidence-source list, not new code.

**Shipped this pass** (six; the two the brief marks high-priority, plus four more the same framework makes cheap once the framework itself is built and tested):
1. **Jira end-of-day update** (mutating, high priority) — reads git/PR/OpenSpec/investigation-continuity/test evidence for the day, drafts a factual Jira comment from a configurable template, supports free-text "offline work" input the user supplies for the routine to fold in, dry-run by default until the user confirms an integration is live, verifies the comment landed before reporting success. Never invents work; asks (via a recorded blocker, not a live prompt — routines run unattended) when work is evidenced but a ticket can't be determined.
2. **Daily technical news digest** (read-only, high priority) — topics from `config.json` (defaults offered at setup, arbitrary custom topics allowed), current search restricted to reputable/authoritative sources, deduplicated, filtered for materiality, no digest generated when nothing material happened (no filler requirement, explicit in the brief).
3. **Weekly status** (read-only) — reuses Groundwork's own completion semantics (`engineering-workflow.md` §3) verbatim: completed/in-progress/blocked/tests/review/merged/deployed/runtime-validated/decisions/next-actions, built only from evidence the same way an interactive completion report would be.
4. **PR/review follow-up** (read-only digest) — awaiting-review, changes-requested, failing CI, stale branch, merge conflicts, completed-but-unmerged; explicitly never claims merged-implies-deployed.
5. **Daily work/TODO digest** (read-only) — git/PR/OpenSpec-task/investigation/Jira/failed-validation evidence only; a weak signal produces no task, not a guessed one.
6. **Documentation drift check** (read-only) — compares implementation against README/architecture/runbook/OpenSpec claims, reports drift found, never auto-rewrites documentation.

**Evaluated and deferred this pass, with reasons** (not silently dropped — recorded in `docs/FUTURE-SCOPE.md`):
- **Task Observer** — the brief's own privacy bar (no raw prompts/code/terminal sessions/full conversations) is right, but detecting a *genuine* repeated pattern reliably needs more structured, cross-session signal than Groundwork's existing telemetry schema captures today (it records tool/agent/validation *classes*, not the sequence-and-timing detail a real pattern-miner needs) — building that safely is a telemetry-schema change with its own privacy review, not a routine. Deferred; the telemetry extension it would need is named as a future candidate, not built speculatively now.
- **Remaining "additional routine discovery" candidates** (cert/PKI expiry, dependency/security advisories, infra drift, cost anomaly, stale-RCA follow-up, release readiness) — scored in `docs/FUTURE-SCOPE.md` against the brief's own criteria (value/reliability/evidence quality/automation safety/external access/noise risk/maintenance cost). None were marked high-priority by the brief; six shipped, well-tested routines is a real, checkable surface — six more at the same time, untested against real Jira/GitHub/cloud accounts (this environment has none), would be exactly the overbuilding the brief warns against.

## E. MCP/integration strategy — documentation only, no live wiring

`docs/INTEGRATIONS.md` (new). Groundwork does not install, configure, or store credentials for GitHub, Spacelift, AWS, GCP, Kubernetes, Terraform, Jira, Confluence, or any observability system — this is unchanged from 2.0's ownership rule ("MCP/external tool access: the task's own environment"), and this environment has no credentials for any of them to test live wiring against regardless (RUNTIME VALIDATION REQUIRED is used honestly, not worked around). What ships is researched, evidence-backed guidance per domain: preferred access (official MCP vs. CLI/API vs. browser fallback), trust tier, auth model, read/write scope, and lazy-loading posture — feeding the capability-resolution model in §B, not a new mechanism of its own.

## F. Curated optional skills — evaluated, nothing auto-installed

`docs/FUTURE-SCOPE.md`, extended. Per the owner's explicit instruction, `wshobson/agents` is recorded as a researched candidate only (from the prior dependency audit), not adopted.

- **Teaching**: `mattpocock/skills`' `teach` skill (github.com/mattpocock/skills, MIT, commit 3 days before this research) is a real, well-built match for §9's brief — a persistent, multi-session teaching workspace (mission/resources/lessons/learning-records) implementing retrieval practice, spacing and interleaving, and it ships `disable-model-invocation: true`, i.e. it is **already lazy/user-invoked-only by its own design** (`/teach`), never auto-triggered. **Recorded as a documented, optional recommendation** (`docs/FUTURE-SCOPE.md`) for anyone who installs it themselves — not installed by Groundwork, and `playbooks/explain.md` is not rewritten to depend on it (EXPLAIN keeps owning routing/evidence per the brief's own framing; the teaching skill, if the user has it, owns technique). This is the one skill candidate researched this pass that clears the adoption bar for a *recommendation*; it still isn't installed automatically, per the "prefer optional installation" instruction.
- **Task Observer**: the canonical implementation (`rebelytics/one-skill-to-rule-them-all`, CC BY 4.0, active) is real, but — confirmed by reading its own source — it is explicitly designed to be **near-always-on** (its own install instructions tell you to add a CLAUDE.md directive invoking it "at the start of any task-oriented session," because description-matching alone under-triggers it) with standing file-write side effects. This independently reinforces §D's deferral: even the best available implementation is shaped the opposite way from Groundwork's context-frugality principle, on top of the telemetry-schema gap already noted. Recorded as researched-and-declined, not silently unmentioned.
- **Security-review, architecture-review, documentation-generation, diagram/presentation**: confirmed to already exist as official (Anthropic `/security-review`, official `code-review`/`feature-dev` plugins, official PPTX skill) or well-established community options — no gap here for Groundwork to fill; playbooks already route to them via the existing capability-resolution order (§B) without needing anything new installed or documented beyond `docs/INTEGRATIONS.md`'s pointer.

## I. Terminal UX

Confirmed live: Groundwork's own scripts (`hooks/*.py`, `scripts/*.py`, `tests/*.py`) import stdlib only — no `requirements.txt`/`pyproject.toml` exists anywhere in the repo today. Adopting any TUI library (Textual, Rich, urwid, blessed) would be Groundwork's first-ever third-party Python dependency, for a feature (`--doctor`'s aligned-column status output) that already works in plain text. **Decision: no new dependency.** `--doctor`/`--routines` output stays a small, stdlib-only plain-text/ANSI-color helper (`sys.stdout.isatty()`/`NO_COLOR`-aware, degrading gracefully for piped/CI output), matching "do not overengineer terminal menus." The existing HTML dashboard remains the richer view for anyone who wants one, unchanged.

## G. setup.sh capability configurator

Extends the existing three-question flow (`choose_profile`/`choose_teams`/`choose_schedule`) with an optional fourth stage: profile-driven capability/routine/news-topic selection, skippable entirely (`./setup.sh` with no interaction still installs the unchanged 2.0 core). Persisted to one new human-readable file, `~/.claude/groundwork/config.json` (pretty-printed, 2-space indent, plain-text, no secrets), written/read/validated by a new `scripts/groundwork_config.py`. **JSON, not YAML** — a deliberate deviation from the brief's own illustrative example, chosen because it matches 100% of Groundwork's existing config-file precedent (`settings.json`, `report.json`) and needs zero new parsing code; the alternative (a hand-rolled YAML-subset parser) would be new, untested infrastructure with its own edge-case surface for a project that has never needed one, for a cosmetic difference the brief itself permits ("choose the actual format based on existing Groundwork conventions"). Pretty-printed JSON is inspectable and hand-editable, which is the actual requirement. Upgrade preserves it (never overwritten by a re-run unless the user re-answers); uninstall removes it (it's Groundwork's own config, not user data, unlike telemetry/reports/investigations).

## H. `setup.sh --doctor` / `--configure` / `--routines`

New modes on the existing mode-dispatch pattern (`--verify`/`--rollback`/`--uninstall` already work this way) — no new CLI framework, no new binary on PATH. `--doctor` extends the existing `verify_install()` function with rows for each configured capability/routine, using real status values (INSTALLED/AVAILABLE/CONFIGURED/CONNECTED/VERIFIED/DISABLED/UNAVAILABLE) and never asserting CONNECTED without an actual check where one is safely possible (e.g., `claude plugin list`/`command -v` for local capabilities; for anything needing real external credentials, reports CONFIGURED, not CONNECTED, since this environment cannot verify further — RUNTIME VALIDATION REQUIRED, stated as such in the row's own detail text, not hidden). `--configure` re-runs the capability-selection question flow standalone (no backup/reinstall). `--routines` lists configured routines, their schedule, and last-run status from telemetry.

## I. Terminal UX

Researched: Groundwork's scripts are stdlib-only Python today (zero third-party dependencies). Adding a real TUI library (Textual, Rich, urwid) would be the first third-party Python dependency this project has ever taken on, for a feature (`--doctor`'s own output, already a clean aligned-column report) that already works well in plain text. **Decision: no new TUI dependency.** `--doctor`/`--routines` output stays plain-text/ANSI-color (already used sparingly elsewhere in `setup.sh`), matching "do not overengineer terminal menus" and "choose the smallest maintainable UX." The existing HTML dashboard remains the answer for anyone who wants a richer view — unchanged, not replaced. "Live activity view" (brief §23) is evaluated separately below.

## J. Live activity view — deferred, documented why

Hooks are event-triggered (confirmed: PreToolUse/PostToolUse/Stop/SubagentStart-Stop/SessionStart/etc.), which could in principle stream a live state view — but composing that into a genuinely reliable "high-level state, not noisy tool-call log" view, updated in near-real-time from a separate terminal, is a materially different and larger engineering surface than everything else in this pass (a background process tailing hook-emitted events, a rendering loop, reconnection/staleness handling) for a capability the brief itself says to skip if the platform doesn't cleanly expose it ("If Claude Code does not expose reliable lifecycle events, do not fake this feature. Document the limitation instead."). Hooks exist; a *reliable, low-effort* live view built from them does not, within this pass's scope. Deferred, recorded in `docs/FUTURE-SCOPE.md` as a real future candidate (the primitives exist; assembling them well is future work), not built speculatively now.

## K. ECC pinning

Shipped: `install.sh` now installs `affaan-m/ECC#v2.2.1` (the latest real, pushed release tag at research time) instead of floating `main`, via the `owner/repo#ref` pin syntax confirmed current on Claude Code's plugin-marketplace path. `GROUNDWORK_ECC_REF` env var overrides it (e.g. back to `main`) for anyone who wants bleeding-edge. Clean-install/upgrade/rollback/uninstall/identity re-proven against the pinned form in this pass's validation (`docs/VALIDATION.md`), not assumed from the unpinned form's prior 2.0 evidence.

## L. What was deliberately not built, and why (summary)

Task Observer (§D), the eight "additional routine discovery" candidates beyond the six shipped (§D), a real TUI (§I), a live activity view (§J), any live-wired MCP integration (§E — no credentials in this environment, and Groundwork doesn't own that wiring anyway), and automatic adoption of any third-party skill including `wshobson/agents` (§F, explicit owner instruction). Each is evidence-based, documented, and reversible — nothing here is a capability gap silently left unmentioned.
