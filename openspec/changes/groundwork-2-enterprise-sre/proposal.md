## Why

This change is the **audit and design phase only** — see `design.md` for the full current-state audit, gap analysis, ECC capability matrix, migration plan, acceptance matrix and open decisions. Nothing in this proposal has been implemented; `tasks.md` is entirely unchecked. Per the requesting brief, Groundwork 2.0 must evolve the existing 1.5.1 architecture in place — it is not a rewrite, and it does not replace anything that already works.

Groundwork 1.5.1 is materially stronger than a typical "governance layer" — its own `docs/VALIDATION.md` shows a genuine evidence-first development discipline (SHA-256 non-regression baselines, adversarial security review, live-transcript proof, honest blocked-task tracking). The audit behind this proposal (full detail in `design.md` §A/§B) found that **most** of the requested Groundwork 2.0 outcomes are already met:

- Evidence-backed reasoning, honest completion truth, deterministic push/review guards, automatic execution-model selection, additive/idempotent install-update-rollback-uninstall, portable (no hardcoded personal identity in shipped code — confirmed by direct code audit), and OpenSpec-used-proportionally are all **VERIFIED, already implemented, and already tested** as of 1.5.1.

Seven concrete, evidence-backed gaps remain, each traced to a specific acceptance criterion in the requesting brief:

1. **A real, currently-shipping bug.** `README.md`/`install.sh`/`setup.sh` state and enforce "Node ≥ 18". VERIFIED against the live OpenSpec npm registry and GitHub source today (2026-09-28): OpenSpec has required **Node ≥ 20.19.0 since at least 1.12.0** (the exact version Groundwork's own CHANGELOG recorded as its 2026-09-20 baseline) — this is not new drift, it is a pre-existing incorrect floor. `install.sh` additionally performs **no Node version check at all** (only `setup.sh` does); a user running `install.sh` directly (documented as the "manual/advanced" path) with Node 18 or 19 gets no warning and a cryptic OpenSpec CLI failure later.
2. **No evidence label for genuinely conflicting or indeterminate evidence.** `evidence-policy.md` §2 has five labels (VERIFIED/UNVERIFIED/ASSUMPTION/INFERENCE/RUNTIME VALIDATION REQUIRED) but no `CONFLICTING EVIDENCE` or bare `UNKNOWN` — confirmed absent repo-wide by direct search. The RCA rule (§7) already correctly refuses to promote a symptom to a root cause, but has no explicit label for "two sources disagree" or "cannot be determined at all."
3. **Independent review is enforced by presence, not by outcome.** `require_material_review.py` (VERIFIED by direct code read) blocks Stop only until *some* reviewer-shaped call appears in the transcript; it does not check that MUST FIX findings were resolved or capture structured review evidence. `engineering-workflow.md` §2.6 already asks for this in rule text — it is advisory only.
4. **No durable record for rejected hypotheses or in-progress investigative work outside OpenSpec.** The 1.1.0 continuation design (`engineering-workflow.md` §7 + `groundwork_session_snapshot.py`) is genuinely strong for MATERIAL engineering work tracked in OpenSpec `tasks.md`, but a TROUBLESHOOT/RCA session — which is typically TRIVIAL/STANDARD tier and therefore *not* OpenSpec-tracked — has nowhere durable for "we ruled out X" to live. Confirmed absent: no test in any of the 5 test files constructs a compaction or fresh-session-recovery scenario, and no mechanism exists to prevent a rejected hypothesis from resurfacing as active after recovery.
5. **ECC is installed and paid for wholesale.** VERIFIED: ECC ships 68 agents / 286 skills (confirmed against the actual published npm tarball, not just the README's claim); Groundwork's own `docs/VALIDATION.md` (1.0.0 evidence) and `docs/TROUBLESHOOTING.md` document this roughly doubling session cost on trivial work with "no config lever that removes it." VERIFIED today: this claim is now **stale** — Claude Code currently ships `skillOverrides`, `Skill()` permission rules, and a skill-level `paths` scoping field, and ECC's own installer supports `--profile`, `--skills`, and `--with capability:*` selection at install time. None of this is used by Groundwork's installer, which always runs a full, uncurated `claude plugin install ecc@ecc`.
6. **No deterministic safety boundary beyond Git.** `docs/FUTURE-SCOPE.md` §10 already names this gap honestly ("more deterministic guards … added one at a time when a real task shows the advisory rule was not enough") and explicitly defers it pending real evidence. This proposal surfaces it as a decision for the owner rather than resolving it unilaterally — see Decision D5 in `design.md`.
7. **Minor, low-risk items**: a byte-for-byte duplicated helper (`dirty_change_names()`) between two hooks; ECC's GitHub `main` (2.2.2, 292 skills) has silently drifted ahead of what npm actually publishes (2.2.1, 286 skills, what `install.sh` actually installs); OpenSpec has released three patch versions (1.12.0 → 1.13.2) since Groundwork's docs were last verified against it.

None of these gaps require new agents, skills, daemons, databases, or a rewrite. Every proposed change is additive or corrective to the existing three-rules-three(4)-hooks-one-installer shape.

## What Changes (subject to the decisions in `design.md` §G — nothing here is authorized for implementation yet)

- **Fix the Node/OpenSpec version claim** — `installer-upstream-compatibility`: correct the documented and enforced floor to match OpenSpec's real requirement, add the missing version check to `install.sh` itself (not just `setup.sh`), and give `setup.sh --verify` a lightweight installed-vs-last-known-good upstream version row (no network call required — compares against a version recorded in the repo at last audit, refreshed manually, matching the existing evidence-verification discipline rather than adding a live network dependency).
- **Extend the evidence taxonomy** — `evidence-taxonomy`: add `CONFLICTING EVIDENCE` and `UNKNOWN` as first-class labels in `evidence-policy.md` §2, make the FACT → EVIDENCE → SOURCE → CLAIM → VALIDATION chain explicit, and strengthen the RCA rule (§7) to require one of these two labels when the evidence genuinely does not support a root cause.
- **Strengthen (not rebuild) the review gate** — `review-evidence-strengthening`: keep `require_material_review.py`'s deterministic presence-check (it works, it is well-tested, it is not being replaced) and add a minimal structured-evidence expectation in rule text plus a narrowly-scoped hook check for the one thing that is deterministically checkable: that a MUST-FIX-bearing review was followed by further work before Stop, not immediately by completion. Full design and the "how far to push determinism" tradeoff is in `design.md` Decision D3.
- **Curate ECC for SRE/CloudOps by policy, using only native, already-existing selection mechanisms** — `ecc-capability-policy`: a small Groundwork-owned classification (CORE SRE / OPTIONAL SRE / LANGUAGE-SPECIFIC / NOT RELEVANT / UNSAFE-FOR-AUTOMATIC-USE, see `design.md` §D) expressed as an install-time ECC profile (`--profile`/`--with capability:*`, ECC's own mechanism) plus, if Runtime Validation confirms it actually suppresses plugin-provided skill invocation (currently UNVERIFIED — Groundwork's own docs assert the opposite from an earlier test), `skillOverrides` entries added by `merge_settings.py`. Groundwork forks nothing and copies no ECC content; it only chooses.
- **Decide, do not silently build, a continuity mechanism for non-OpenSpec-tracked work** — `investigation-continuity`: `design.md` Decision D2 lays out the two real options (extend the existing git/OpenSpec-only model's reach vs. add one small, capped, opt-in investigation-state artifact for TROUBLESHOOT/AUDIT-class work) with evidence for and against each, and does not pick one — this is presented as a genuine owner decision per Groundwork's own autonomy rule.
- **Decide, do not silently build, deterministic safety beyond Git** — `deterministic-safety-expansion`: `design.md` Decision D5 presents a narrowly-scoped candidate (mirroring exactly how `block_protected_push.py` was built and validated — pattern-detect a specific, well-understood bypass class, fail-open, adversarially tested) and explicitly recommends against a broad "block risky cloud commands" mechanism as out of proportion with current evidence.
- **Small maintainability fix**: extract the duplicated `dirty_change_names()` helper shared by `require_material_review.py` and `groundwork_session_snapshot.py` into one place.
- **Documentation correction**: refresh ECC (2.2.1, npm-published) and OpenSpec (1.13.2) version references, and note the GitHub-main-vs-npm-publish drift risk for ECC.
- **New tests**: compaction/fresh-session-recovery scenarios (rejected hypothesis stays rejected is a named, explicit test case), conflicting-evidence and bare-UNKNOWN classifier cases, Node-version enforcement in `install.sh`, and — only if the corresponding decision is taken — ECC-profile install tests and the new safety hook's adversarial bypass tests.

## Capabilities

### New Capabilities
- `evidence-taxonomy`: the extended evidence label set (adds CONFLICTING EVIDENCE, UNKNOWN) and the explicit FACT→EVIDENCE→SOURCE→CLAIM→VALIDATION chain.
- `ecc-capability-policy`: how Groundwork selects a curated, SRE/CloudOps-relevant subset of ECC's agents/skills at install time using ECC's and Claude Code's own native selection mechanisms.
- `installer-upstream-compatibility`: correct, enforced Node/Python/OpenSpec version floors and a lightweight upstream-drift check.
- `review-evidence-strengthening`: minimal structured evidence for the independent-review gate, without rebuilding it.
- `investigation-continuity`: DECISION-PENDING — how (if at all) rejected hypotheses and in-progress non-OpenSpec-tracked investigative state survive compaction and fresh sessions.
- `deterministic-safety-expansion`: DECISION-PENDING — whether and how far to extend deterministic (hook-enforced) safety beyond Git.

### Modified Capabilities
- `project-continuation` (proposed in `openspec/changes/intelligent-engineering-harness`, not yet archived — see `design.md` §H, Open Question 1): gains the continuity decision's outcome once made.
- `validation-and-review-evidence` (same predecessor change): gains the review-evidence-strengthening outcome.
- `harness-installation` (same predecessor change): gains the corrected Node/OpenSpec version floor and the upstream-drift check.
- `usage-telemetry` (archived, `openspec/specs/usage-telemetry/spec.md`): no schema change proposed at this stage; noted as a candidate to record `evidence_conflict` / `review_evidence` flags in a later phase only if real usage shows the gap (see `design.md` §E Phase 4).

## Impact

- **Files** (once a phase is approved and implemented — nothing changes in this design-only submission): `rules/evidence-policy.md`, `rules/engineering-workflow.md`, `hooks/require_material_review.py`, `hooks/groundwork_session_snapshot.py` (+ new shared helper module), `install.sh`, `setup.sh`, `README.md`, `docs/ARCHITECTURE.md`, `docs/FUTURE-SCOPE.md`, `docs/VALIDATION.md`, `CHANGELOG.md`, `tests/test_hooks.py`, `tests/test_setup.py`, new `tests/test_continuity.py` (or extension of an existing file — TBD in Phase design). A new hook file only if Decision D5 is taken; no new state file unless Decision D2 picks that option.
- **Installed footprint**: no new top-level directories; at most one new hook file (D5) and, only if D2 selects the state-file option, one small capped file under `~/.claude/groundwork/`.
- **No new agents, skills, daemons, databases, or message buses** in any option under consideration.
- **Compatibility**: fixing the Node floor changes what `setup.sh`/`install.sh` will refuse to run on — this is a **breaking correction** for any environment currently running Groundwork against Node 18/19 with a real `openspec/` workflow (their OpenSpec CLI calls are almost certainly already failing today; this only makes the failure surface earlier, at install time, with a clear message instead of downstream). Documented as a compatibility note in the migration plan (`design.md` §E, Phase 1).
